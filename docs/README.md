# Documentation Integration Strategy

This directory explains how TI SDK documentation is made agent-accessible and how hardware documents (TRM, datasheet, schematics) integrate with skills.

---

## Why this matters

An agent without access to the TRM and schematic is guessing at register values and pin names. An agent with them can:

- Look up the exact PADCONFIG register offset for a pin
- Verify that a schematic net name maps to the correct K3 domain GPIO
- Quote the exact memory map region a peripheral uses
- Confirm clock source mismatch before writing DT nodes

This is the single biggest quality gap between a skill that produces plausible output and one that produces correct output.

---

## TI SDK documentation formats

| Source | Format | Location |
|---|---|---|
| Processor SDK Linux Docs | Sphinx RST → HTML | `<sdk>/docs/` or `software-dl.ti.com` |
| TRM (e.g. SPRUIV7A) | PDF | ti.com/lit (download manually) |
| Datasheet (e.g. SPPSD17) | PDF | ti.com/lit |
| SysConfig output | CSV / JSON | Generated by SysConfig tool |
| Board schematic | PDF / KiCad | From board vendor / TI reference design |
| App notes | PDF | ti.com/lit |

## Strategy 1: Pre-converted SDK documentation snippets (low maintenance)

The `docs/snippets/` directory contains hand-curated markdown extracts from the SDK docs. These are small, focused sections that skills reference directly.

**Maintained by:** TI SDK skills team (update when SDK doc changes)
**Update frequency:** once per SDK release
**How to use:** skills `Read` the relevant snippet file directly

Current snippets:

| File | Source | Content |
|---|---|---|
| `snippets/boot-flow.md` | SDK Linux Kernel Users Guide | Boot flow, DT selection, extlinux.conf format |
| `snippets/pinmux-register-guide.md` | AM625 TRM (SPRUIV7) §GPIO | PADCONFIG bit fields, AM625_IOPAD macro, RXACTIVE bit |
| `snippets/remoteproc-guide.md` | SDK Remoteproc Guide | remoteproc sysfs interface, firmware loading, trace buffer |
| `snippets/yocto-layer-guide.md` | SDK Yocto Build Guide | bbappend pattern, FILESEXTRAPATHS, SRC_URI, layer structure |
| `snippets/emmc-layout.md` | SDK Linux Kernel Users Guide | eMMC partition layout, boot0 sector offsets |

### How to add a snippet

1. Find the relevant section in the SDK HTML docs at `<sdk>/docs/`
2. Use `docs/convert.sh` to convert RST source to clean markdown
3. Trim to only the content that agents need (1-3 pages max per snippet)
4. Add an entry to this README

## Strategy 2: Live HTML fetch via MCP (zero maintenance)

When a skill needs content from the live TI SDK documentation website, the MCP server's `fetch` tool can retrieve and parse the HTML on demand.

**Used for:** full procedure pages, API references, release notes
**Requires:** network access to `software-dl.ti.com`
**Latency:** ~2s per page fetch

Example skill instruction:
```
If the user needs the full Yocto build procedure, fetch:
https://software-dl.ti.com/processor-sdk-linux/esd/AM62X/latest/exports/docs/linux/Foundational_Components/Yocto/Yocto_Layer_Configuration.html
```

## Strategy 3: Hardware documents via documents block (highest accuracy)

Register the TRM, datasheet, and schematic in the active target profile's `documents:` block (see `target-platform/platform_template.yaml`).

Skills that need register-level accuracy instruct the agent to:
1. Open `documents.trm` at the relevant chapter
2. Read the specific table (e.g., PADCONFIG register bit fields)
3. Apply the value from the document rather than from training data

This eliminates hallucination of register offsets and bit positions.

### Recommended documents to register

| Field | Document | Why it matters |
|---|---|---|
| `trm` | AM625 TRM (SPRUIV7A) | PADCONFIG bits, memory map, peripheral register reference |
| `datasheet` | AM625 Datasheet (SPPSD17) | Pinout table, GPIO ball assignments, electrical specs |
| `board_schematic` | SK-AM62x Schematic | Net names → connector → SoC ball mapping |
| `sysconfig_pinout_csv` | SysConfig exported CSV | Exact mux mode and signal for each pad |
| `errata` | AM625 Errata | Workarounds for known silicon bugs |

### Where to get TI documents

All TI documents are free at: https://www.ti.com/product/AM6254#design-development

Direct PDF links (search by document ID):
- TRM: search `SPRUIV7` at ti.com/lit
- Datasheet: search `SPPSD17` at ti.com/lit  
- Errata: search `SPRZ463` at ti.com/lit (AM625 errata)

## Strategy 4: Machine-readable hardware data (highest usability)

Pre-extracted machine-readable YAML files in `references/hardware/` allow skills to look up hardware facts without parsing PDFs.

| File | Source | Content |
|---|---|---|
| `references/hardware/am625-pinmux-registers.yaml` | TRM SPRUIV7 §GPIO | All PADCONFIG registers: address, default, bit fields |
| `references/hardware/sk-am62x-connectors.yaml` | SK-AM62x Schematic | RPi header pinout, USB-C, JTAG, all named connectors |
| `references/hardware/am625-memory-map.yaml` | TRM §Memory Map | Key peripheral base addresses, MSMC, DDR regions |
| `references/hardware/trm-chapter-index.md` | TRM SPRUIV7 ToC | Chapter and section numbers for fast PDF navigation |

**How to maintain:** update when a new SoC/board is added. The YAML files are manually extracted from the documents once and then remain stable (register maps rarely change between TRM revisions).

## Converting RST documentation to Markdown

The SDK ships Sphinx RST source for its documentation. Use `convert.sh` to convert to markdown for snippet creation.

```bash
# Prerequisites: pandoc, python3-sphinx (not needed if using HTML output)

# Convert a single RST file
./docs/convert.sh <sdk-path>/docs/linux/Foundational_Components/Kernel/Kernel_Drivers/GPIO.rst

# Convert an HTML page (recommended — avoids RST cross-references)
./docs/convert.sh https://software-dl.ti.com/processor-sdk-linux/esd/AM62X/latest/exports/docs/...
```

Output goes to `docs/snippets/<source-name>.md`.

---

## What NOT to include

- Full TRM or datasheet text. These are 1000+ pages. Include only extracted tables and key sections.
- Verbatim SDK HTML. Convert to markdown and trim.
- Binary schematic files. Extract connector tables to YAML instead.
- SysConfig GUI outputs. Export to CSV and reference via `documents.sysconfig_pinout_csv`.

- [ ] Update `references/errata/` with new known issues
