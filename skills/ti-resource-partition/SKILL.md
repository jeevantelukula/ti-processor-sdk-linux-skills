# K3 resource partitioning

The tool divides SoC resources between software hosts (A53, R5, ...). Docs: it assigns DMA channels,
rings, proxies and interrupts, and sets Quality of Service (QoS) for devices. This skill documents
only what can be verified in the SDK tree. The tool's own user guide is the authority for running it.

File names and counts below are examples from the AM62P SDK 12.02.00.01.01; yours will differ.
Always list the tree first (step 1).

## Docs (MCP)

Follow [../../context/mcp-usage.md](../../context/mcp-usage.md): pass `device`, `os`, `version`
explicitly (`device=$TI_DOCS_DEVICE`, `os="linux"`, `version=$TI_SDK_VERSION_DOCS` if
`ti_processor_sdk_docs_list_versions` has it, else `"latest"`; the MCP lags the SDK).

- `ti_processor_sdk_docs_search(query="K3 resource partitioning tool", device=$TI_DOCS_DEVICE, os="linux", version=<ver>)`,
  then read the hit. Example path (AM62PX, latest): `linux/How_to_Guides/Host/K3_Resource_Partitioning_Tool.html`.
  The page is a few lines long and links an external "K3 Resource Partitioning Tool user guide" for usage.
  If search finds no such page for the device, the device docs do not cover the tool: say so.
- `ti_processor_sdk_docs_search(query="DMA channel ring allocation host QoS", ...)` for related context.

## Prerequisites

- SDK installed; `source <skills-root>/lib/ti-sdk-env.sh` (`TI_SDK_ROOT`, `TI_SOC`, `TI_UBOOT_SRC_DIR`).
  Tool path: `$TI_SDK_ROOT/board-support/k3-respart-tool/`. If it does not exist, this SDK does not
  ship the tool; do not borrow another SoC's files.
- To run the tool: TI SysConfig and the user guide linked from the docs. The `.syscfg` header names
  the product and tool version (example: `K3-RESOURCE-CONFIGURATION@1.0.0`, tool `1.21.2`). No CLI is
  documented in the SDK tree or the docs page, so none is given here.
- Per-device facts: generated KB (`$TI_KB`, via `ti-generate-kb`) if present, else the SDK tree.

## Steps

### 1. Inspect what the SDK ships

```
T=$TI_SDK_ROOT/board-support/k3-respart-tool
cat $T/manifest.txt ; ls -a $T $T/out ; ls $T/.meta/data/*/ ; ls $T/.meta/modules/*/
head -n 8 $T/out/*.syscfg           # @cliArgs line: device, package, product, tool version
```

Generic layout (same on every SDK that ships the tool; verify with the `ls` above):

| Path | What it is |
|---|---|
| `out/<name>.syscfg` | SysConfig configuration: host modules (A53, R5, ...) with per-resource counts and `resourceSharing` instances |
| `out/<soc>_qos.h` | Generated header "Keystone3 Quality of service endpoint definitions, Auto generated by K3 Resource Partitioning Tool": QoS endpoint base addresses. The QoS values are not in it; they go into U-Boot's `<soc>_qos_uboot.c` (step 3) |
| `.meta/modules/` | SysConfig modules; per-SoC host definitions in a `.meta/modules/<soc>/` subdirectory |
| `.meta/data/<soc>/` | SoC data JSON (`Resources`, `Hosts`, `HostNames`, `Qos`, `Firewall`, `BWlimiters`, `ResDependencies`, `DeviceName`) |
| `.meta/templates/` | Output templates (`.xdt`), e.g. `rm-cfg`, `qos_header`, `qos_config_uboot`, `firewall_config` |
| `manifest.txt` | Package date and baseline commit |

Example (AM62P SDK): `out/am62p-evm.syscfg` (hosts `A53_2`, `MCU_0_R5_0`, `WKUP_0_R5_1`) and
`out/am62p_qos.h`. Do not hand-edit generated outputs or `.meta`; treat `.meta` as tool internals.
Counts inside the `.syscfg` are board/SDK specific: read them from your file, do not quote these.

### 2. How the QoS output enters the build (find consumers in U-Boot source)

The SDK `Makefile`, `makerules` and `Rules.make` should not invoke the tool; check with
`grep -ril respart $TI_SDK_ROOT/Makefile $TI_SDK_ROOT/makerules $TI_SDK_ROOT/Rules.make` (example: empty
in the AM62P SDK, so the top-level build does not run it). Locate where the QoS data is consumed:

```
cd $TI_UBOOT_SRC_DIR
grep -rl 'k3_qos_data\|K3_QOS_REG' arch/arm/mach-k3          # per-SoC *_qos_uboot.c
grep -rn 'setup_qos' arch/arm/mach-k3                         # definition and per-SoC callers
find arch/arm/mach-k3 -name '*_qos*'
```

Example - the consumer is the R5 SPL: `arch/arm/mach-k3/r5/<soc>/<soc>_qos_uboot.c`
(`struct k3_qos_data qos_data[]`, `K3_QOS_REG`/`K3_QOS_VAL`), a copy of the header next to it
(with a license banner, so not byte-identical to `out/`), and `setup_qos()` in
`arch/arm/mach-k3/common.c` (guarded by `CONFIG_K3_QOS`, enabled in the R5 defconfig; check with
`grep -n K3_QOS $TI_UBOOT_SRC_DIR/configs/<r5 defconfig>`), called from the SoC init file. In the same SDK the
grep finds QoS tables only for some SoCs; a SoC with no `*_qos_uboot.c` has no U-Boot QoS table in this SDK.

### 3. Change QoS settings (U-Boot R5 SPL table)

The two U-Boot files have different roles; never copy one over the other. Evidence (upstream U-Boot,
e.g. `arch/arm/mach-k3/r5/am62px/`; check yours with the `find` above):

| U-Boot file | Holds | Comes from |
|---|---|---|
| `<soc>_qos.h` | endpoint base addresses only (`#define <ENDPOINT> 0x...`), banner "Auto generated by K3 Resource Partitioning Tool" | tool's QoS header output (`qos_header` template; `out/<soc>_qos.h` in the SDK) |
| `<soc>_qos_uboot.c` | the settings: `struct k3_qos_data qos_data[] = { .reg = K3_QOS_REG(<ENDPOINT>, <ch>), .val = K3_QOS_VAL(qos, orderid, asel, epriority, virtid, atype) }`, then `u32 qos_count = ARRAY_SIZE(qos_data);`; `#include`s the header | tool's U-Boot QoS output (`qos_config_uboot` template); `/* modules_qosConfigN */` comments name the `.syscfg` instances |

`K3_QOS_REG`/`K3_QOS_VAL` and `struct k3_qos_data` are in `arch/arm/mach-k3/include/mach/k3-qos.h`.

1. Back up both files (changes the boot image; confirm with the user first):
   `cp <soc>_qos.h <soc>_qos.h.orig; cp <soc>_qos_uboot.c <soc>_qos_uboot.c.orig`
2. Change the QoS instances in the `.syscfg` with SysConfig and generate the outputs (procedure and output
   location: the tool's user guide; no CLI is documented, see Prerequisites).
3. Header: only if the generated endpoint list differs, update `<soc>_qos.h` from it, keeping the U-Boot SPDX
   banner. Compare first: `diff <(grep '^#define' out/<soc>_qos.h) <(grep '^#define' <U-Boot>/<soc>_qos.h)`.
4. Table: replace the entries inside `qos_data[] = { ... };` of `<soc>_qos_uboot.c` with the generated ones; keep
   the `#include` lines and the `qos_count` line. If the tool produced no U-Boot table file, stop and tell the
   user: the header alone does not carry any QoS value.
5. `CONFIG_K3_QOS=y` must be in the R5 defconfig (grep above), then rebuild the R5 stage (`make u-boot-r5`, or
   `make u-boot` where the makerule has no separate R5 target; see `ti-build-source`) and deploy `tiboot3.bin`
   with `ti-deploy-image`.

DMA channel, ring and interrupt allocation is a different output (`rm-cfg` template; U-Boot keeps a
`board/ti/<soc-dir>/rm-cfg.yaml`, see `ti-custom-board-port`). How a regenerated `rm-cfg` is meant to replace
it is not documented in the SDK tree or the docs page; read the user guide rather than assume.

## Verify

- `diff <soc>_qos_uboot.c.orig <soc>_qos_uboot.c`: only `.reg`/`.val` entries changed; includes and
  `qos_count` intact. Same for the header if it was touched.
- The R5 build compiles `<soc>_qos_uboot.c` without errors (a missing `qos_data`/`qos_count` or an
  undefined endpoint macro fails here, before anything reaches the board).
- Deploy `tiboot3` and confirm the board still boots to Linux; keep the `.orig` files and the previous
  `tiboot3.bin` to roll back.
- Check `dmesg` for DMA/ti-sci errors after boot; the expected clean output is defined in the user guide.

## Troubleshooting

- Tool outputs not picked up by the SDK build: expected, nothing in `Makefile`/`makerules` invokes
  the tool; U-Boot consumes only the copied QoS header/table.
- `board-support/k3-respart-tool` missing, or its `out/` and `.meta/.../<soc>/` names do not match
  `$TI_SOC`: use only that SDK's own tool contents, and say what is missing.
- A docs page of a few lines is the real content; usage is in the external user guide.
